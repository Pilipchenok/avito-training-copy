# avito-kitchen

Бэкенд-сервис для оформления заказов еды и координации их приготовления между покупателями и ресторанами-партнёрами (MVP).

---

## Быстрый запуск

```bash
# Сборка образов, применение миграций со стартовыми данными и запуск
make up
```

Сервисы поднимаются на следующих портах:
* `:8080` — основной API (`kitchen`)
* `:8081` — эмулятор кухни партнёра (`restaurant`)
* `:5432` — база данных (`postgres`)

### Пример создания заказа

```bash
curl -i -X POST http://localhost:8080/api/v1/client/orders \
  -H "Content-Type: application/json" \
  -d '{
    "restaurant_id": "a0eebc99-9c0b-4ef8-bb6d-6bb9bd380a11",
    "delivery_address": "ул. Тверская, д. 7",
    "items": [
      {
        "menu_item_id": "b0eebc99-9c0b-4ef8-bb6d-6bb9bd380a22",
        "quantity": 2
      }
    ]
  }'
```

После создания заказа сервис асинхронно отправляет вебхук в `restaurant`, который меняет статус заказа.

## Архитектура

Код разделен на три слоя:
* `internal/handler` — транспортный HTTP-слой на стандартном `net/http`, сериализация JSON, маппинг ошибок в HTTP-коды.
* `internal/service` — валидация переходов статуса заказа, координация его создания, фоновая отправка вебхуков.
* `internal/repository` — сырые SQL-запросы через `pgxpool`, транзакции и пессимистические блокировки.

## Жизненный цикл заказа

Переходы состояний проверяются до обращения к базе данных:

* Валидные переходы: `CREATED -> COOKING`, `COOKING -> READY`, `CREATED -> CANCELLED`, `COOKING -> CANCELLED`.
* Невалидные переходы: попытка перескочить шаг (`CREATED -> READY`), откат назад (`READY -> COOKING`), отмена готового заказа (`READY -> CANCELLED`). При нарушении возвращается `400 Bad Request` (`INVALID_ORDER_STATUS`).

## Ограничения и компромиссы (Trade-offs)

1. **Доставка вебхуков:** Отправка уведомления на кухню выполняется в отдельной горутине с таймаутом в 5 секунд.

2. **Корзина:** Ограничена одним заведением в рамках одного заказа.

3. **Целочисленная финансовая арифметика** Отказ от float32 в пользу int из-за рисков погрешности

4. **Односторонняя нотификация кухни:** Вызов кухни платформой реализован в одностороннем порядке через горутину `notifyRestaurant` с фиксированным таймаутом.

5. **Стартовые данные в `init.sql`:** Базовые сущности (рестораны, меню) инициализируются непосредственно в миграции.

Инструменты генеративного ИИ применялись в режиме ассистента исключительно для рутинных задач кодогенерации и подготовки тестов:

* **Линтер:** валидация и исправление схемы конфигурации `.golangci.yml`.

Весь сгенерированный код прошел, статический анализ и валидацию через детектор гонок (`go test -race`).
